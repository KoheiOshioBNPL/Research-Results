# API入口のチェックリスト

OWASP API Security Top 10 2023 の見方。各入口に、コードで確認できるものだけを当てる。

深刻度:

- 先に直す: 他人の資源、管理機能、トークン未検証、呼び出し元由来のURL取得
- 一緒に直す: 項目の出しすぎ、詳細エラー、CORS、無制限の件数や再試行
- 未確認: ミドルウェアやポリシーがこの差分の外にあり、まだ読んでいない

## 認証 API2

- この入口に認証が要るか。付いているなら、そのミドルウェアがこのメソッドに掛いているか
- トークンを使うなら、署名、有効期限、発行者、宛先、アルゴリズムの固定、失効のどれを見ているか
- 資格情報をクエリ文字列で受けていないか
- APIキーはアプリの識別であり、利用者本人の認可の代わりになっていないか
- パスワード再設定、ログイン、招待は、回数と失敗回数の上限があるか

直し方: 入口の手前で主体を確定し、期限切れと失効を拒否する。本人の認可は別の検査に残す。

## オブジェクト認可 API1

- IDで1件を読む、更新する、消すときに、その主体がその資源の当事者かをサーバーが照合しているか
- 一覧が、クライアントの渡した `userId` だけで絞り込まれていないか
- 複数ID、ネストした `/users/{id}/orders/{id}` も、各IDで同じ照合があるか
- 検索やフィルタの結果から、他人の資源が混ざらないか

直し方: 永続化の直前に、主体と資源の関係を条件に含める。クライアントが送った所有者IDは採用しない。

## プロパティ認可 API3

- レスポンスが永続化オブジェクトの全フィールド展開になっていないか。許可した項目だけを返しているか
- 更新がリクエストボディの展開になっていないか。ロール、残高、状態、所有者など権限のある項目をクライアントが書けないか
- 未知のフィールドを無視するか拒否するかが決まっていて、権限項目はどちらでも入らないか

直し方: 読む許可リストと書く許可リストを分ける。欠席したキーを「消せ」の意味にしない。

## 機能認可 API5

- 返金、削除、権限変更、公開設定は、役割または権限をサーバーで見ているか
- 同じ処理の GET だけ検査して、POST、PUT、PATCH、DELETE が無検査になっていないか
- GraphQL なら、フィールドとミューテーションごとに同じ検査があるか

直し方: 機能ごとに許可を調べる。ルーティングの隠蔽は許可に数えない。

## 資源消費 API4

- ボディサイズ、ページサイズ、配列の長さ、クエリの深さに上限があるか
- クライアントの配列を無制限に展開して、メール、SMS、決済、外部APIを呼んでいないか
- 認証、再設定、招待、本人確認に回数の上限があるか

直し方: 上限を入口に置き、呼び出し元ごとに数える。

## 業務フロー API6

- 購入、予約、ポイント、在庫、招待のように、成功すると事業が変わる操作に、連続実行の歯止めがあるか
- 同じリクエストの再送で、二重に確定しないか（冪等キー）

直し方: 速度と回数の上限、および確定処理の冪等性をサーバーに置く。

## サーバーが外へ取りに行く API7

- リクエスト由来のURL、ホスト、ファイルパスを、サーバーがそのまま取得・接続していないか
- 取得が必要なら、許可したホストだけか。リンクローカルやクラウドのメタデータアドレスを弾いているか

直し方: 呼び出し元のURLを取得しない。必要な宛先はサーバー側の許可リストにする。

## 設定 API8

- ブラウザ向けなら、資格情報付きのリクエストに `Access-Control-Allow-Origin: *` を返していないか
- エラーがスタック、SQL、内部パス、他利用者の識別子を返していないか
- デバッグ、計測、管理用の入口が本番のルータに載っていないか
- 既定の秘密や例示の鍵を本番設定が使っていないか

直し方: 本番設定を開発用の便利さから分ける。エラーは利用者向けの短いメッセージにする。

## 在庫 API9

- 追加した入口が、公開しているルート一覧またはスキーマに入っているか
- 古い版が、現行より弱い認証や認可のまま残っていないか

直し方: 使わない版とデバッグ入口を外す。残す版には現行と同じ検査を付ける。

## 他APIの利用 API10

- 決済、本人確認、地図などの応答を、署名と期待する項目で検証してから権限や表示に使っているか
- 外部が返したURLやHTMLを、そのまま利用者へ渡していないか

直し方: 許可した項目だけを受け取る。外部の成功フラグだけで権限を上げない。

## Webhook

- 署名、時刻、再送、同じイベントの二重処理を見ているか
- 相手のURLをこちらから取りに行く設計なら、API7 と同じ境界として扱う

## GraphQL と gRPC

- GraphQL は深さ、件数、別名による増幅の上限があるか。イントロスペクションを本番で出すかが決まっているか
- gRPC はメソッドごとの認可があるか。メタデータ上の資格情報を、HTTPヘッダと同じ水準で検証しているか
